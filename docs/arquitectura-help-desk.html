Help Desk · Arquitectura y funcionamiento

Aplicación Angular para gestionar solicitudes de soporte: tickets, tablero Kanban, dashboard de indicadores y administración de usuarios, conectada a una API externa (Django) con autenticación por token.

Angular 22Angular Material / CDK 22Standalone + Signals RxJS 7.8TypeScript 6SCSSVitestSin zone.js

1. Visión general

Qué hace la aplicación y con qué decisiones técnicas está construida.

Qué resuelve

Registrar y seguir solicitudes de soporte. Cada ticket tiene asunto, descripción, estado (Abierto, En proceso, Cerrado), prioridad (Baja, Media, Alta) y fecha de creación.

Quién la usa

Tres perfiles: Usuario (solo consulta), Soporte (gestiona tickets y usa el Kanban) y Administrador (además Reportes y Usuarios).

Pantallas

Login, Dashboard, Tickets (listado, detalle, formulario), Kanban, Usuarios (listado, detalle, formulario), Reportes (pendiente), Acerca de, 404 y Acceso restringido.

Decisiones técnicas principales

DecisiónQué significa en este proyecto
Componentes standaloneNo hay NgModule. Cada componente declara sus imports. Es la forma actual de Angular.
SignalsEl estado de pantalla (cargando, error, listas, filtros del dashboard y del Kanban) vive en signal() y se deriva con computed().
Sin zone.jsAngular repinta cuando cambia un signal o cuando ocurre un evento de plantilla. Un campo normal modificado desde una suscripción no repinta, por eso el estado asincrónico se guarda en signals.
Carga bajo demandaTodas las páginas se cargan con loadComponent. El Kanban (con datepicker y drag & drop) es un chunk aparte.
API externaLos datos vienen de un backend Django por HTTPS (API_BASE_URL en config/api.ts). Los tickets del listado se paginan y filtran en el servidor.
Reglas en un solo lugarQué se puede editar o eliminar vive en models/ y en Sesion; rutas, menú y botones consultan las mismas funciones.

2. Arquitectura en capas

Las dependencias van siempre hacia abajo: una página usa componentes compartidos y servicios; los servicios usan HttpClient; el interceptor decora cada petición antes de llegar a la API.

Regla de dependenciasLas páginas no llaman a HttpClient directamente: siempre pasan por un servicio. Los componentes compartidos no conocen la API: reciben datos por input() y avisan con output(). Esa separación hace que los compartidos se puedan probar y reutilizar sin servidor.

4. Cómo arranca y cómo funciona la aplicación

Del arranque a la primera pantalla, y qué ocurre en cada petición.

4.1 Arranque

  1. main.ts llama a bootstrapApplication(App, appConfig). No hay módulo raíz.
  2. app.config.ts registra dos proveedores: provideRouter(routes) y provideHttpClient(withInterceptors([tokenInterceptor])). También escucha errores globales del navegador.
  3. El componente raíz App pinta la shell: barra superior con la marca y «Cerrar sesión», menú lateral (visible solo con sesión) y <router-outlet>.
  4. El router resuelve la URL. La ruta vacía redirige a /dashboard; si no hay sesión, sesionGuard la convierte en /login.
  5. Al entrar a una ruta, Angular descarga el chunk de esa página (loadComponent), la instancia y ejecuta su ngOnInit, que normalmente pide datos a un servicio.

4.2 Autenticación y ciclo de una petición

El 401 del login no redirigeEl interceptor solo actúa en recursos protegidos (/tickets, /usuarios, /usuario del mismo origen). Un 401 de /auth/token significa «credenciales incorrectas» y lo muestra el propio Login.

5.4 La sesión

  • Sesion guarda { rol, token, username } en un signal de solo lectura (actual).
  • iniciarSesion() llama a POST /auth/token y valida la respuesta: rechaza roles desconocidos o ausencia de token.
  • Se persiste en sessionStorage (clave help-desk.sesion) para sobrevivir a una recarga (F5). La lectura valida la forma de los datos y tolera que el almacenamiento no exista.
  • puedeGestionarTickets es un computed derivado de ROLES_GESTION_TICKETS; menú, botones y rutas usan la misma lista.
Los guards no son seguridad realUn guard solo ordena la navegación en el navegador. La autorización verdadera (quién puede borrar un ticket) debe validarla la API con el token en cada petición.

6.3 Respuesta paginada

interface PaginaTickets {
  count: number;          // total de tickets que cumplen los filtros (no solo los de la página)
  next: string | null;
  previous: string | null;
  results: Ticket[];      // los de la página pedida

6.4 Interceptor

tokenInterceptor es una función (HttpInterceptorFn) que se ejecuta en cada petición:

  1. Sin token en la sesión → deja pasar la petición sin cambios.
  2. Resuelve la URL y comprueba que el origen sea el de la API y que la ruta empiece por tickets, usuarios o usuario. Si no, no agrega nada (el token nunca viaja a otros orígenes ni a /auth/token).
  3. Clona la petición con Authorization: Bearer <token>.
  4. Si la respuesta es 401, cierra la sesión, navega a /login y relanza el error.

7. Estado y reactividad

Cada pantalla es dueña de su estado y lo expone con signals. No hay un store global: lo único compartido es la sesión.

7.1 El patrón «cargando / error / datos»

Todas las pantallas que consultan la API usan tres signals y una plantilla con @if / @else if / @else:

cargando = signal(true);
error    = signal(false);
tickets  = signal<Ticket[]>([]);

cargar() {
  this.cargando.set(true); this.error.set(false);
  this.servicio.obtener().subscribe({
    next:  d => { this.tickets.set(d); this.cargando.set(false); },
    error: e => { console.error(e); this.error.set(true); this.cargando.set(false); }
  });
}

En la plantilla: @if (cargando()) { … } @else if (error()) { … } @else { …datos… }.

7.2 Dos estrategias de filtrado

Servidor — Tickets

El volumen puede ser grande, así que cada cambio de página, tamaño o filtro hace una petición con page, page_size y los filtros. La tabla solo guarda la página actual.

Cliente — Kanban y Dashboard

Cargan todos los tickets una vez y derivan con computed(). Un filtro no hace red: recalcula en memoria.

8. Componentes por tipo

Qué hace cada uno, qué recibe y cómo funciona por dentro.

8.1 Shell de la aplicación — App

Estructura fija: mat-toolbar (marca + «Cerrar sesión - rol»), mat-sidenav y router-outlet.

  • El menú solo se abre con sesión: [opened]="sesion.actual() !== null".
  • Submenú Tickets (Listado / Crear ticket) con su propio signal ticketsAbierto; se abre solo si la ruta activa pertenece al grupo.
  • Visibilidad por rol: Kanban para Soporte/Administrador; Reportes y Usuarios solo Administrador; «Crear ticket» solo si puedeGestionarTickets().
  • cerrarSesion() limpia la sesión y navega a /login.

8.2 Páginas (componentes contenedor)

Una página conoce servicios, rutas y diálogos; delega la presentación en componentes compartidos.

Login

formulario por plantillaSesion

Formulario usuario/contraseña con ngModel. entrar() ignora entradas vacías o un envío en curso, llama a Sesion.iniciarSesion() y, si todo sale bien, borra la contraseña y navega a /dashboard. Los errores se traducen según el código HTTP (0 → sin conexión/CORS, 400/401 → credenciales, 403, 429, otro).

Dashboard

signals + computedTicketService

Carga todos los tickets (takeUntilDestroyed). Filtro único de prioridad. Muestra 4 indicadores por estado, 3 de seguimiento (pendientes, alta prioridad pendiente, % cerrado), una «lectura operacional» en texto y 4 gráficos: por estado (barras), pendientes y cerrados (anillo), pendientes por prioridad (barras) y creados por día (líneas). Botón «Actualizar datos».

Tickets (listado)

paginación servidorMatTabledebounce

Filtros de texto (espera 300 ms), estado, prioridad y rango de fechas; botón de vista rápida tickets críticos (Abierto + Alta, una sola consulta); bloque «En esta página» con contadores por estado; tabla con IdTicket, EstadoTicket, PrioridadTicket y AccionesTicket; paginador conectado al total del servidor. Cancela la consulta anterior al lanzar otra y retrocede de página si la última queda vacía tras eliminar.

TicketForm

formularios reactivoscrear/editarConfirmDialog

Un único componente para crear y editar (según haya :id en la ruta). Validaciones: asunto 5–100, descripción 10–500. Recorta espacios antes de guardar y conserva la fecha original al editar. Un ticket Cerrado se muestra bloqueado. Cancelar compara los valores con los iniciales: sin cambios vuelve directo; con cambios pide confirmación. Los errores HTTP se muestran con su motivo.

TicketDetalle

solo lectura

Lee :id, carga el ticket y lo presenta con etiquetas de estado y prioridad. «Editar» solo aparece a Soporte/Administrador y se deshabilita (con tooltip) si el ticket está cerrado.

Kanban

CDK drag & dropfiltros clientelazy chunk

Tablero de tres columnas. Filtros: texto, estado, prioridad y rango de fechas (Material datepicker). Cada columna se ordena por fecha, del más reciente al más antiguo. Mientras carga muestra un contador de segundos en vivo. Al soltar una tarjeta en otra columna se hace un PUT y solo cuando el servidor confirma se actualiza la lista (no hay actualización optimista); mientras hay un guardado en curso todo el tablero queda bloqueado.

Usuarios · UsuarioForm · UsuarioDetalle

CRUDborrado lógico

Listado con RolUsuario, estado y acciones. «Eliminar» no borra: hace PATCH estado='Eliminado' tras confirmar y avisa con InfoDialog. El formulario solo ofrece Vigente/Bloqueado; un usuario Bloqueado o Eliminado se muestra bloqueado (aun por URL directa). Las reglas salen de models/usuario.ts.

Reportes · AcercaDe · NotFound · SinAcceso

Reportes es un marcador («Próximamente»). AcercaDe describe el sistema. NotFound es la página 404 (rutas desconocidas). SinAcceso es el destino cuando un guard de roles rechaza.

9.1 Listado de tickets con paginación y filtros del servidor

9.2 Formulario de ticket: estados y salida

9.3 Cambiar el estado en el Kanban

  1. El usuario arrastra una tarjeta (por el asa) o usa el selector de la tarjeta.
  2. KanbanColumna.soltarTicket() descarta movimientos dentro de la misma columna, fuera del contenedor o durante un guardado; si procede, emite cambiarEstado.
  3. Kanban.actualizarEstado() ignora el cambio si no cambia el estado o si ya hay un guardado en curso; marca actualizandoID y envía un PUT con el ticket completo.
  4. Éxito: reemplaza el ticket en el signal tickets con la respuesta; los computed reubican la tarjeta. Error: la tarjeta no se mueve y se muestra un aviso.

9.4 Eliminar un ticket

  1. AccionesTicket emite eliminar(ticket) (solo si el perfil puede gestionar).
  2. Tickets.eliminar() vuelve a comprobar el permiso y abre ConfirmDialog.
  3. Si el usuario confirma: marca eliminandoId, llama a DELETE; al confirmar el servidor recarga la página actual y abre InfoDialog.

11. Estilos y tema

  • Tema Material 3 con mat.theme() en styles.scss (paleta azure, tipografía Roboto). Genera variables --mat-sys-*.
  • Tokens propios --hd-* (radio, espacio, superficie, fondo, borde, texto suave, sombra) definidos a partir de las variables de Material: cambiar la paleta cambia toda la app.
  • Clases globales compartidas: .pagina, .encabezado, .tarjeta, .tabla-contenedor, .mensaje, .error, además de h1, h2, p y a.
  • Estilos por componente (.scss encapsulado): solo lo propio. Los componentes compartidos usan tokens para respetar el tema; algunos acentos (azul, ámbar, verde, rojo de los estados) siguen con colores fijos.
  • Presupuestos de estilo: aviso a 4 kB y error a 8 kB por componente.

14. Limitaciones conocidas y mejoras sugeridas

SeguridadEl token se guarda en sessionStorage, legible por cualquier script de la página. Es aceptable mientras no se cargue código de terceros; una alternativa más robusta es una cookie HttpOnly emitida por el backend. La autorización final debe validarla siempre la API.
  • Confirmación de salida del formulario: solo cubre el botón Cancelar. Salir por el menú o con «Atrás» pierde los cambios sin preguntar; para cubrirlo haría falta un guard canDeactivate.
  • URL de la API fija en código: cambiar de entorno requiere editar config/api.ts. Se podría mover a environment por configuración de build.
  • Reportes es un marcador sin funcionalidad.
  • Supuestos sobre la API: nombres de filtros y de paginación (page, page_size, texto, fechaDesde, fechaHasta), ruta /tickets/paginados y forma de los usuarios (estado, fechaCreacion) se tomaron del código y no se verificaron contra el backend real. Los ids se declaran como texto aunque Django suele entregar números; funciona porque nunca se comparan con textos.
  • Dashboard y Kanban cargan todos los tickets: con volúmenes grandes convendrá agregar los totales en el servidor.
  • Peso del bundle inicial por encima de la recomendación de 500 kB; la mayor parte es Angular Material.
