1Qué vamos a construir

Una visión general antes de escribir una sola línea: pantallas, tecnologías y las ideas que se aprenden.

Help Desk es una aplicación para registrar y seguir solicitudes de soporte (tickets) y administrar a las personas que las atienden (usuarios). Es un proyecto ideal para aprender Angular porque reúne en un solo lugar casi todo lo que se usa en el trabajo real: rutas, formularios, tablas, llamadas a una API, componentes reutilizables y pruebas.

Las pantallas

RutaComponenteQué hace
/dashboardDashboardPortada con accesos rápidos.
/ticketsTicketsTabla paginada con acciones: Detalle, Editar, Eliminar.
/tickets/nuevoTicketFormFormulario para crear un ticket.
/tickets/editar/:idTicketFormEl mismo formulario, cargando un ticket existente.
/tickets/:idTicketDetalleFicha de solo lectura de un ticket.
/usuarios, /usuarios/nuevo, /usuarios/editar/:id, /usuarios/:idUsuarios, UsuarioForm, UsuarioDetalleLo mismo que tickets, pero para usuarios (con borrado lógico).
/kanban, /reportesKanban, ReportesSecciones reservadas ("Próximamente").
/acerca-deAcercaDeInformación del sistema.
cualquier otraNotFoundPágina de error 404.

Tecnologías

  • Angular 22: componentes standalone (sin módulos), signals y plantillas con @if/@for.
  • Angular Material 22: toolbar, menú lateral, tabla, paginador, formularios, diálogos e íconos.
  • SCSS para los estilos, apoyado en las variables CSS del tema de Material.
  • RxJS y HttpClient para hablar con la API.
  • json-server: una API REST falsa que lee y escribe el archivo db.json.
  • Vitest con ng test para las pruebas.
Sin zone.js

Este proyecto no incluye zone.js (no aparece en package.json). Angular 22 trabaja por defecto sin él. La consecuencia práctica es importante: si cambias un campo normal de la clase, la pantalla no se repinta sola. Por eso todo el estado de las pantallas usa signals. Lo verás una y otra vez en el manual.

2Preparar el entorno y crear el proyecto

Instalar las herramientas y generar el esqueleto de la aplicación.

Necesitas Node.js (con npm) y un editor como VS Code. Todo lo demás se instala desde la terminal.

  1. Instala el CLI de Angular (una sola vez en tu equipo).
  2. Crea el proyecto. Cuando pregunte por el formato de estilos, elige SCSS.
  3. Agrega Angular Material: instala el tema, los íconos y las tipografías.
  4. Instala json-server, que será nuestra API de pruebas.
terminal
# 1. CLI de Angular (una sola vez)
npm install -g @angular/cli

# 2. Crear el proyecto (elige SCSS)
ng new help-desk
cd help-desk

# 3. Angular Material
ng add @angular/material

# 4. API simulada
npm install json-server

# Comprobar que todo arranca: http://localhost:4200
npm start
Las preguntas del asistente cambian

Las preguntas exactas de ng new y ng add varían entre versiones. Lo que importa es elegir SCSS y aceptar el tema de Material. Si algo no coincide, guíate por el resultado que describe este capítulo.

Dónde va cada cosa y por qué. Una buena estructura ahorra horas de búsqueda.

Todo el código vive en src/app, organizado por responsabilidad, no por tipo de archivo:

CarpetaRegla para decidir si algo va aquí
models/Describe la forma de los datos (interface) y las reglas que dependen solo de ellos (puedeEditar).

Pruébalo

Antes de crear un componente nuevo pregúntate: ¿tiene su propia URL? Si sí, va en pages/. Si solo se pega dentro de otras pantallas, va en shared/.

4Modelos de datos y <code>db.json</code>

Antes de dibujar pantallas, define qué datos existen y cómo se ven.

Un modelo es una interface de TypeScript: no genera código, solo le dice al compilador qué forma tienen los datos. Así, si escribes mal un nombre de campo, el error aparece al escribir y no cuando un usuario hace clic.

src/app/models/ticket.ts
export interface Ticket {
    id: string;
    asunto: string;
    descripcion: string;
    estado: 'Abierto' | 'En proceso' | 'Cerrado';
    prioridad: 'Baja' | 'Media' | 'Alta';
    fechaCreacion: string;
}

// Para crear un ticket todavía no existe el id: lo asigna la API.
export type NuevoTicket = Omit<Ticket, 'id'>;

Tres ideas en pocas líneas

  • Tipos literales ('Abierto' | 'En proceso' | 'Cerrado'): el campo solo admite esos valores. Escribir 'Abirto' es un error de compilación.
  • Omit<Ticket, 'id'>: "un Ticket sin el campo id". Se deriva del modelo, así que si agregas un campo a Ticket, NuevoTicket lo recibe automáticamente.
  • El id es string, no number: así lo entrega json-server ("id": "1"). Declararlo como número fue uno de los primeros errores.

El modelo de usuario sigue el mismo patrón y agrega un estado:

src/app/models/usuario.ts
export interface Usuario {
    id: string;
    nombre: string;
    email: string;
    rol: 'Administrador' | 'Soporte' | 'Usuario';
    // 'Eliminado' es un borrado lógico: el registro se conserva en la API.
    estado: 'Vigente' | 'Bloqueado' | 'Eliminado';
    fechaCreacion: string;
}

export type NuevoUsuario = Omit<Usuario, 'id'>;

5La API simulada con json-server

Un backend de mentira que se comporta como uno de verdad, y un truco para numerar los usuarios.

json-server ofrece, sin escribir código, las operaciones CRUD sobre cada recurso de db.json:

OperaciónMétodo y URLQué hace
ListarGET /usuariosDevuelve todos.
Leer unoGET /usuarios/3Devuelve el de id 3.
CrearPOST /usuariosAgrega el cuerpo JSON enviado.
ReemplazarPUT /usuarios/3Sustituye todo el registro.
ModificarPATCH /usuarios/3Cambia solo los campos enviados.
BorrarDELETE /usuarios/3Elimina el registro.

Arrancarla

Necesitas dos terminales: una para la API y otra para Angular.

terminal 1 (API)

# La API queda en http://localhost:3000
terminal 2 (Angular)
npm start
# La app queda en http://localhost:4200
Pruébalo

Abre http://localhost:3000/tickets en el navegador: verás el JSON crudo. Es la misma respuesta que recibirá Angular.

El problema de los ids correlativos

Se quería que los usuarios nuevos recibieran el id 9, 10, 11… y no un código al azar. El primer intento fue calcular el siguiente número en Angular y enviarlo en el POST. No funcionó: revisando el código de json-server 1.0.0-beta.15 se ve por qué.

node_modules/json-server/lib/service.js (fragmento)
async create(name, data = {}) {
    // ...
    const item = { ...data, id: randomId() };   // el id enviado se sobrescribe
    items.push(item);
    await this.#db.write();
    return item;
}
Error común: confiar en el id del POST

En esta versión de json-server el POST siempre pone un id aleatorio. Y PUT/PATCH conservan el id de la URL, así que tampoco sirven para cambiarlo. La numeración correlativa no se puede resolver desde Angular: hay que hacerla en el servidor.

La solución es un pequeño script que arranca json-server igual que siempre, pero antes envuelve el método create: deja que json-server cree el registro y enseguida reemplaza el id por mayor + 1.

api/server.mjs
import { Service } from 'json-server/lib/service.js';

// Colecciones con id correlativo.
const COLECCIONES_CORRELATIVAS = ['usuarios'];

const crearOriginal = Service.prototype.create;

Service.prototype.create = async function (name, data = {}) {
  const item = await crearOriginal.call(this, name, data);
  if (!item || !COLECCIONES_CORRELATIVAS.includes(name)) return item;

  // Solo cuentan los ids formados por dígitos; los aleatorios antiguos se ignoran.
  const mayor = this.find(name, { where: {} }).reduce((max, registro) => {
    if (registro === item || !/^\d+$/.test(String(registro.id))) return max;
    return Math.max(max, Number(registro.id));
  }, 0);

  item.id = String(mayor + 1);
  return this.patchById(name, item.id, {});   // vuelve a guardar el archivo
};

// Con el parche aplicado, se inicia json-server normalmente.
await import('json-server/lib/bin.js');
package.json (fragmento)
"scripts": {
  "start": "ng serve",
  "api": "node api/server.mjs db.json",
  ...
}

Como no hay ningún await entre calcular y asignar el id, dos altas simultáneas nunca obtienen el mismo número (se probó con dos altas simultáneas, que recibieron números distintos).

Dos advertencias
  • El script modifica una parte interna de una librería en beta. Si la actualizas, vuelve a comprobar que la numeración sigue funcionando.
  • Si arrancas la API con npx json-server db.json en lugar de npm run api, los ids vuelven a ser aleatorios.

6Arranque de la app, proveedores y rutas

main.ts, app.config.ts y app.routes.ts: lo que Angular necesita antes de mostrar nada.

El punto de entrada

En una aplicación standalone no hay AppModule. main.ts arranca el componente raíz y le pasa la configuración global:

src/main.ts
import { bootstrapApplication } from '@angular/platform-browser';
import { appConfig } from './app/app.config';
import { App } from './app/app';

bootstrapApplication(App, appConfig)
  .catch((err) => console.error(err));

Los proveedores globales

Aquí se "enciende" lo que usará toda la aplicación. Sin provideHttpClient(), cualquier servicio que pida HttpClient falla con un error de inyección.

src/app/app.config.ts
export const appConfig: ApplicationConfig = {
  providers: [
    provideBrowserGlobalErrorListeners(),
    provideRouter(routes),     // habilita el router con nuestra tabla de rutas
    provideHttpClient()        // habilita HttpClient
  ]
};

La tabla de rutas

Cada ruta asocia una URL con el componente que se muestra en el <router-outlet>.

src/app/app.routes.ts (fragmento)
export const routes: Routes = [
    { path: '', redirectTo: 'dashboard', pathMatch: 'full' },
    { path: 'dashboard', component: Dashboard },
    { path: 'tickets', component: Tickets },
    { path: 'tickets/nuevo', component: TicketForm },
    { path: 'tickets/editar/:id', component: TicketForm },   // mismo componente, otra URL
    { path: 'tickets/:id', component: TicketDetalle },       // va DESPUÉS de nuevo y editar
    { path: 'usuarios', component: Usuarios },
    { path: 'usuarios/nuevo', component: UsuarioForm },
    { path: 'usuarios/editar/:id', component: UsuarioForm },
    { path: 'usuarios/:id', component: UsuarioDetalle },
    { path: '**', component: NotFound }                      // siempre al final
];
El orden importa

Angular recorre las rutas de arriba hacia abajo y usa la primera que coincide. Si tickets/:id estuviera antes que tickets/nuevo, la URL /tickets/nuevo se interpretaría como "el ticket cuyo id es nuevo". Por la misma razón ** (cualquier URL) va última.

Error común: la ruta literal

Una vez se escribió path: 'ticket/id'. Eso es una ruta literal: nunca recibe un parámetro. El parámetro se declara con dos puntos: tickets/:id.

7Los servicios: hablar con la API

Un servicio concentra las llamadas HTTP para que los componentes no sepan nada de URLs.

Un servicio es una clase con @Injectable. Con providedIn: 'root' existe una sola instancia para toda la app y cualquier componente puede pedirla con inject().

src/app/services/ticket.ts
@Injectable({
    providedIn: 'root'
})
export class TicketService {
    private http = inject(HttpClient);
    private apiUrl = 'http://localhost:3000/tickets';

    // Read - Get
    obtenerTickets(): Observable<Ticket[]> {
        return this.http.get<Ticket[]>(this.apiUrl);
    }
    obtenerTicket(id: string): Observable<Ticket> {
        return this.http.get<Ticket>(`${this.apiUrl}/${id}`);
    }
    // Create - Post
    crearTicket(ticket: NuevoTicket): Observable<Ticket> {
        return this.http.post<Ticket>(this.apiUrl, ticket);
    }
    // Update - Put
    actualizarTicket(id: string, ticket: Omit<Ticket, 'id'>): Observable<Ticket> {
        return this.http.put<Ticket>(`${this.apiUrl}/${id}`, ticket);
    }
    // Delete - Delete
    eliminarTicket(id: string): Observable<void> {
        return this.http.delete<void>(`${this.apiUrl}/${id}`);
    }
}

Lo que hay que entender

  • get<Ticket[]>(…): el genérico le dice a TypeScript qué trae la respuesta. Sin él el resultado sería Object y el compilador no te ayudaría.
  • Un Observable es perezoso: llamar a obtenerTickets() no hace la petición. Se hace cuando alguien llama a .subscribe(). Es el error clásico de "no pasa nada".
  • CRUD ↔ HTTP: crear = POST, leer = GET, actualizar = PUT/PATCH, borrar = DELETE.
  • El componente decide cuándo llamar; el servicio decide cómo.

El servicio de usuarios es igual, con una diferencia de diseño: "eliminar" no hace DELETE. Solo cambia el estado a Eliminado usando PATCH, que modifica un campo sin reenviar el resto:

src/app/services/usuario.ts (fragmento)
// "Eliminar" usuario es un borrado lógico: solo cambia el estado.
eliminarUsuario(id: string): Observable<Usuario> {
    return this.http.patch<Usuario>(`${this.apiUrl}/${id}`, { estado: 'Eliminado' });
}
Error común: inject() mal escrito

En las primeras versiones el servicio tenía private http = Inject(HttpClient); (con mayúscula y sin importar), además de repetir http en el constructor, y this.http.get(Ticket[](this.apiUrl)), que no es sintaxis válida. La forma correcta es inject(HttpClient) en minúscula y get<Ticket[]>(url).

El submenú de Tickets

export class App {

  alternarTickets(): void {
    this.ticketsAbierto.update((abierto) => !abierto);
  }
}

¿Por qué exact: true en "Listado"?

Sin él, /tickets/nuevo también "empieza con" /tickets y los dos ítems quedarían resaltados. exact exige que la URL sea idéntica.

Error común: el ícono que se ve como texto

El chevron del submenú mostraba la palabra "expa". Causa: matListItemMeta está pensado para texto (un contador, una fecha) y aplica la fuente de etiqueta pequeña, que tiene más prioridad que la fuente de íconos. Al ponerlo directamente sobre <mat-icon>, el nombre del ícono se dibuja como letras. Solución: envolver el ícono en un <span matListItemMeta>, como en el ejemplo.

Que el layout ocupe toda la altura

En vez de calcular 100vh - 64px a mano (el alto del toolbar cambia en móvil), la raíz se vuelve una columna que ocupa toda la ventana, y el contenedor toma el espacio restante:

src/app/app.scss (fragmento)
:host {
    display: flex;
    flex-direction: column;
    height: 100vh;
}

.layout {
    flex: 1 1 auto;
    min-height: 0;        // necesario para que el contenido pueda hacer scroll
}

9Estilos: tema, variables y clases compartidas

Cómo se organiza el CSS para que cambiar un color sea tocar un solo lugar.

Encapsulación de estilos

Un .scss de componente solo afecta a su propia plantilla: Angular agrega un atributo único a cada elemento y a cada selector. Por eso .imagen en un componente no choca con .imagen en otro. La contrapartida: para estilar un elemento que crea Material por dentro (como las celdas de la tabla) hay que hacerlo en el CSS global, y esa es la razón de que las reglas de .tabla-contenedor estén en styles.scss.

Overlaps y cómo evitarlos

Una causa frecuente de elementos "encimados" fue sobrescribir con display:flex el layout interno de mat-list-item. Regla práctica: no redefinas el display de un componente de Material; envuélvelo en un elemento tuyo y dale layout a ese elemento.

10Signals y el patrón "cargando / error / datos"

El patrón que se repite en cada pantalla que lee de la API.

Un signal es una caja que guarda un valor y avisa a Angular cuando cambia. Se lee llamándolo como función (cargando()) y se modifica con .set() o .update().

ejemplo
cargando = signal(true);          // crear con valor inicial
cargando();                       // leer           → true
cargando.set(false);              // reemplazar
contador.update((n) => n + 1);    // calcular a partir del valor anterior

Casi toda pantalla que lee datos pasa por tres estados y los muestra con @if:

cargando→datos listos→o→error
patrón en el componente
cargando = signal(true);
error = signal(false);

cargarTickets(): void {
  this.cargando.set(true);
  this.error.set(false);          // al reintentar, se limpia el error anterior

  this.ticketService.obtenerTickets().subscribe({
    next: (tickets) => {
      this.dataSource.data = tickets;
      this.cargando.set(false);
    },
    error: (err) => {
      console.error('Error al obtener los tickets: ', err);
      this.error.set(true);
      this.cargando.set(false);
    },
  });
}
patrón en la plantilla
@if (cargando()) {
  <p class="mensaje">Cargando tickets...</p>
} @else if (error()) {
  <div class="mensaje error">No fue posible obtener los registros</div>
} @else {
  <!-- aquí se dibuja la tabla -->
}
Error común: campos normales sin zone.js

Las primeras versiones usaban cargando = true; y this.cargando = false; (campos normales). La pantalla se quedaba en "Cargando…" para siempre, porque sin zone.js nadie avisa a Angular de que el valor cambió dentro del subscribe. Con signals el aviso es automático.

Pruébalo

Detén la API (Ctrl+C en la terminal 1) y recarga /tickets: debe aparecer el mensaje de error, no una pantalla en blanco. Vuelve a arrancarla y recarga.

Error común: una columna sin definición

Conectar el paginador

El paginador está dentro del @else, o sea que no existe mientras la pantalla muestra "Cargando…". Si lo pidieras en ngOnInit con un @ViewChild normal, sería undefined y la tabla no paginaría. La solución es un setter: Angular lo ejecuta en el momento en que el paginador aparece.

@ViewChild(MatPaginator)
set paginator(paginador: MatPaginator | undefined) {
  if (paginador) {
    this.dataSource.paginator = paginador;
  }
}

12Formularios reactivos: crear y editar con el mismo componente

FormBuilder, validadores, mensajes de error y cómo un componente sirve para dos rutas.

Un formulario reactivo se define en TypeScript (los campos y sus reglas) y la plantilla solo se enlaza a él. Es más verboso que otros enfoques, pero muy fácil de probar y de validar.

src/app/pages/ticket-form/ticket-form.ts (fragmento)
private fb = inject(FormBuilder);

ticketForm = this.fb.nonNullable.group({
  asunto: ['', [Validators.required, Validators.minLength(5), Validators.maxLength(100)]],
  descripcion: ['', [Validators.required, Validators.minLength(5), Validators.maxLength(500)]],
  estado: ['Abierto' as Ticket['estado'], Validators.required],
  prioridad: ['Media' as Ticket['prioridad'], Validators.required],
});
  • nonNullable: los valores nunca son null. Así encajan con la interfaz NuevoTicket.
  • 'Abierto' as Ticket['estado']: le dice a TypeScript que el valor inicial es del tipo literal, no un string cualquiera.

Un componente, dos modos

Las rutas tickets/nuevo y tickets/editar/:id usan el mismo componente. La diferencia: si la URL trae :id, se está editando.

¿La URL trae :id?→sí: cargar el ticket y rellenar el formulario→no: formulario vacío
src/app/pages/ticket-form/ticket-form.ts (fragmento)
private route = inject(ActivatedRoute);

ticketId = this.route.snapshot.paramMap.get('id');       // null al crear
cargando = signal(!!this.ticketId);                       // solo carga si edita

ngOnInit(): void {
  if (!this.ticketId) return;

  this.ticketService.obtenerTicket(this.ticketId).subscribe({
    next: (ticket) => {
      const { id, fechaCreacion, ...datos } = ticket;     // separa el id y la fecha
      this.fechaCreacion = fechaCreacion;
      this.ticketForm.patchValue(datos);                  // rellena los campos
      this.cargando.set(false);
    },
    error: () => { this.error.set(true); this.cargando.set(false); },
  });
}

guardar(): void {
  if (this.ticketForm.invalid) {
    this.ticketForm.markAllAsTouched();                   // muestra todos los errores
    return;
  }

  const ticket: NuevoTicket = {
    ...this.ticketForm.getRawValue(),
    fechaCreacion: this.fechaCreacion || new Date().toISOString().slice(0, 10),
  };

  const peticion = this.ticketId
    ? this.ticketService.actualizarTicket(this.ticketId, ticket)   // PUT
    : this.ticketService.crearTicket(ticket);                      // POST

  peticion.subscribe({
    next: () => this.router.navigate(['/tickets']),
    error: () => { this.error.set(true); this.guardando.set(false); },
  });
}
¿Por qué markAllAsTouched()?

Material solo muestra el error de un campo cuando fue "tocado". Si el usuario pulsa Guardar con todo vacío, ningún campo se tocó, y no vería por qué no se guarda. markAllAsTouched() los marca todos de una vez.

Pruébalo

Abre /tickets/nuevo, pulsa Guardar con el formulario vacío y comprueba que aparecen los mensajes. Luego edita un ticket y mira cómo el título cambia a "Editar Ticket".

Cuando el mismo trozo de interfaz aparece en varias pantallas (la etiqueta de color del estado, el "#id" que enlaza al detalle), se convierte en un componente de shared/. Recibe datos con input() y avisa con output().

Un componente que avisa: output()

AccionesTicket dibuja los botones Detalle, Editar y Eliminar. No sabe cómo eliminar (eso es de la pantalla y del servicio): solo avisa que el usuario lo pidió.

src/app/shared/acciones-ticket/acciones-ticket.ts
export class AccionesTicket {
  ticket = input.required<Ticket>();
  eliminando = input(false);                  // el padre lo activa mientras procesa
  eliminar = output<Ticket>();                // evento hacia el padre

  editable = computed(() => puedeEditar(this.ticket()));
  motivoNoEditable = MOTIVO_NO_EDITABLE;

  solicitarEliminacion(): void {
    this.eliminar.emit(this.ticket());
  }
}
en el padre
<app-acciones-ticket [ticket]="ticket"
                     [eliminando]="eliminandoId() === ticket.id"
                     (eliminar)="eliminar($event)" />
hijo: emit(ticket)→(eliminar)="eliminar($event)"→padre: confirma y llama a la API
Regla de oro

Los datos bajan por input(); los eventos suben por output(). El componente compartido no llama a la API ni navega por su cuenta: eso lo decide quien lo usa.

Error común: nombres de clase y de archivo que no coinciden

El componente de prioridad nació como copia del de estado y quedó con tres fallos que nadie veía porque no se usaba: styleUrl: './prioridad-ticket.css' (el archivo es .scss), un carácter | suelto en la plantilla y un SCSS con clases .estado.abierto que no coincidían con las del HTML. Un componente sin usar puede estar roto sin avisar: en cuanto lo importes en una pantalla, el compilador lo revisa.

15Reglas de negocio: "un ticket cerrado no se edita"

Dónde poner una regla para que se cumpla en todas partes, no solo en un botón.

La regla se escribe una sola vez, junto al modelo, como función pura:

src/app/models/ticket.ts
export const MOTIVO_NO_EDITABLE = 'Los tickets cerrados no se pueden editar';

// Regla única: un ticket cerrado no se edita.
export function puedeEditar(ticket: Pick<Ticket, 'estado'>): boolean {
    return ticket.estado !== 'Cerrado';
}

Si mañana la regla cambia (por ejemplo, "también los 'En proceso' de prioridad Alta"), se modifica aquí y se actualizan todas las pantallas. Se aplica en tres capas, porque desactivar el botón no basta:

CapaQué evitaCómo
Listado y detalleHacer clic en "Editar".Enlace deshabilitado con tooltip.
FormularioEscribir /tickets/editar/3 en la barra de direcciones.Al cargar el ticket, si no es editable se deshabilita el formulario y se muestra el motivo.
guardar()Que el estado cambie mientras el formulario está abierto.Comprueba bloqueado() antes de enviar.

Deshabilitar un enlace

Un <a> no tiene [disabled] como un botón. Con Material, un mat-icon-button sobre un <a> sí acepta [disabled]; y poner routerLink en null evita que navegue:

src/app/shared/acciones-ticket/acciones-ticket.html

     [routerLink]="editable() ? ['/tickets/editar', ticket().id] : null"
     [disabled]="!editable()"
     aria-label="Editar ticket">

</span>
Esto es solo la interfaz

La API (json-server) no valida nada. Alguien que llame al PUT directamente puede modificar un ticket cerrado. Una protección real tiene que estar también en el backend. Las reglas del frontend mejoran la experiencia; no son seguridad.

El flujo completo de "Eliminar"

clic en Eliminar→ConfirmDialog→¿confirmó?→llamada a la API→recargar tabla→InfoDialog
src/app/pages/tickets/tickets.ts (fragmento)
private dialog = inject(MatDialog);

eliminar(ticket: Ticket): void {
  this.dialog
    .open<ConfirmDialog, ConfirmDialogData, boolean>(ConfirmDialog, {
      data: {
        titulo: 'Eliminar ticket',
        mensaje: `¿Estás seguro de eliminar el ticket "${ticket.asunto}"? Esta acción no se puede deshacer.`,
        textoConfirmar: 'Eliminar',
      },
    })
    .afterClosed()                         // Observable que emite true / false al cerrar
    .subscribe((confirmado) => {
      if (confirmado) this.eliminarTicket(ticket);
    });
}

private eliminarTicket(ticket: Ticket): void {
  this.eliminandoId.set(ticket.id);        // deshabilita el botón de esa fila

  this.ticketService.eliminarTicket(ticket.id).subscribe({
    next: () => {
      this.eliminandoId.set(null);
      this.cargarTickets();

      // El aviso solo aparece cuando la API confirmó la eliminación
      this.dialog.open<InfoDialog, InfoDialogData>(InfoDialog, {
        data: { titulo: 'Ticket eliminado', mensaje: `El ticket "${ticket.asunto}" se eliminó correctamente.` },
      });
    },
    error: (error) => {
      console.error('Error al intentar eliminar el ticket:', error);
      this.eliminandoId.set(null);
    },
  });
}
Los tres genéricos de open<…>

open<ComponenteDelDialogo, TipoDeLosDatos, TipoDelResultado>. Con ellos, data se valida al escribir y confirmado llega tipado como boolean en vez de any.

Pruébalo

Elimina un ticket: primero ves el diálogo rojo de confirmación; al aceptar, la tabla se actualiza y aparece el aviso azul. Prueba "Cancelar" y comprueba que no pasa nada.

17Usuarios: el mismo patrón, con estados

Después de tickets, usuarios es repetir el recorrido con otro modelo. Estas son las diferencias.

Una vez que Tickets funciona, Usuarios es casi un copiar-adaptar: el mismo listado paginado, el mismo formulario crear/editar, el mismo detalle. Conviene construirlo así: primero una entidad completa, después la segunda. Lo que cambia:

TemaTicketsUsuarios
EstadoAbierto, En proceso, CerradoVigente, Bloqueado, Eliminado
Qué impide editarEstado CerradoEstado distinto de Vigente (Bloqueado o Eliminado)
EliminarDELETE realBorrado lógico: PATCH con estado: 'Eliminado'
IdAleatorio de json-serverCorrelativo (gracias a api/server.mjs)
EtiquetasEstadoTicket, PrioridadTicketRolUsuario (y el estado con clases globales)
src/app/models/usuario.ts
export const MOTIVO_NO_EDITABLE = 'Los usuarios bloqueados no se pueden editar';
export const MOTIVO_ELIMINADO = 'Los usuarios eliminados no se pueden editar';

// Solo un usuario Vigente se puede editar.
export function puedeEditar(usuario: Pick<Usuario, 'estado'>): boolean {
    return usuario.estado === 'Vigente';
}

// Un usuario ya eliminado no se vuelve a eliminar.
export function puedeEliminar(usuario: Pick<Usuario, 'estado'>): boolean {
    return usuario.estado !== 'Eliminado';
}

// Texto del tooltip cuando "Editar" está deshabilitado.
export function motivoNoEditable(usuario: Pick<Usuario, 'estado'>): string {
    return usuario.estado === 'Eliminado' ? MOTIVO_ELIMINADO : MOTIVO_NO_EDITABLE;
}
Borrado lógico

En lugar de destruir el registro, se marca como Eliminado. Ventajas: se conserva el historial, se puede auditar quién existió y una eliminación por error es recuperable. Es una decisión de diseño habitual en sistemas de gestión.

Un efecto de la regla

Como un usuario Bloqueado no se puede editar, tampoco se puede volver a Vigente desde el formulario. Si lo necesitas, agrega una acción aparte ("Desbloquear"). Lo mismo pasa con los tickets cerrados y una posible acción "Reabrir".

20Ruta de construcción: hazlo tú desde cero

El orden recomendado para reconstruir la aplicación, con una comprobación en cada paso.

No avances al siguiente paso hasta que la comprobación del actual funcione. Es mucho más fácil encontrar un error cuando solo hay una cosa nueva.

  1. Proyecto y Material. ng new, ng add @angular/material.
    Comprobación: npm start muestra la página de bienvenida.
  2. Modelos y db.json. Interfaces Ticket y Usuario.
    Comprobación: npm run api y abrir localhost:3000/tickets.
  3. Rutas y componentes vacíos. Genera las páginas, escribe app.routes.ts.
    Comprobación: escribir cada URL muestra "… works!".
  4. Layout. Toolbar, mat-sidenav y router-outlet.
    Comprobación: el menú navega y resalta la ruta activa.
  5. Servicio de tickets. obtenerTickets() con HttpClient.
    Comprobación: mostrar el resultado en consola.
  6. Listado. Tabla + paginador + estados cargando/error.
    Comprobación: detén la API y verifica el mensaje de error.
  7. Formulario. Crear con validaciones.
    Comprobación: el nuevo ticket aparece en db.json.
  8. Editar y detalle. Reutiliza el formulario con :id; crea la pantalla de detalle.
    Comprobación: editar cambia el registro.
  9. Eliminar. Primero con confirm(); después con los diálogos.
    Comprobación: cancelar no elimina.
  10. Componentes compartidos. Estado, prioridad, id, acciones.
    Comprobación: la tabla se ve igual que antes, con menos HTML.
  11. Reglas de negocio. puedeEditar en las tres capas.
    Comprobación: un ticket cerrado no se edita ni por URL.
  12. Usuarios. Repite el recorrido (pasos 5 a 11) con el nuevo modelo.
  13. Estilos. Tema, variables y clases compartidas; limpia los hexadecimales.
  14. Pruebas. Un .spec.ts por componente y servicio.
    Comprobación: ng test en verde.

Lista para verificar antes de dar por terminado

  • npx ng build compila sin errores.
  • npx ng test --watch=false pasa todas las pruebas.
  • Cada pantalla maneja los tres estados: cargando, error y datos.
  • Ningún componente usa HttpClient directamente (siempre un servicio).
  • No quedan colores en hexadecimal en los componentes (salvo los semánticos, como el rojo de eliminar).
  • Los formularios muestran mensajes de error por cada validación.
